## Result

Conversions now report `balanced`, `not_balanced` or `cannot_check` against
printed statement figures. The engine uses a pure Decimal reconciliation
function, checks printed subtotals and running balances, and reports signed
calculated-minus-printed differences. Deposit opening/closing figures are
required; cards require all six printed equation terms. Missing figures are
never assumed to be zero.

JSON and previews carry reconciliation evidence, per-row provenance and a coarse
layout. XLSX keeps the in-memory writer and adds live Checks formulas plus cell
notes. CSV keeps its original six columns. All five locales show plain-language
status and highlighted suspect rows, including flagged rows beyond the initial
50-row preview. There are no confidence percentages or new marketing/privacy
claims. Production billing availability and the 100-page cap remain intact.

The existing Umami `convert-success` event sends only `balanced`
(`yes` / `no` / `unknown`) and allowlisted coarse `layout`
(`deposit_table`, `deposit_lines`, `card_table`, `card_lines`, `unknown`). No
amounts, dates, names, descriptions, file names or account IDs are sent.

**Silent errors: 0. False alarms: 0. Missing rows: 0. Extra rows: 0.**
The ten original layouts retain 100% exact ordered rows. Each comparison checks
date, description, signed amount, running balance, currency, type and row order,
including duplicates. A silent error means `balanced` while any row differs;
a false alarm means correct rows shown `not_balanced`. Every complete synthetic
fixture must also be balanced, so an unknown status cannot hide a regression.

The corpus includes Chase, Citi, Capital One and American Express-style card
families with posting/transaction dates, sectioned or minus-signed payments,
and separate fees/interest. Variations cover December-to-January periods
(including a year printed only once), multiline descriptions, page breaks with
repeated headers, no activity, overdrafts, amounts at least 1,000,000.00, and
40 pages. Fixtures are generated only from invented data.

The original `accuracy-report.json` list format remains available. New
`accuracy-family-report.json` and `accuracy-report.md` provide the aggregate
table; CI uploads all three reports. Generated PDFs and workbooks stay under
ignored `work/` and are not committed. No real statement was used or uploaded.

## XLSX verification

Opened engine-generated `deposit.xlsx` and `card.xlsx` using openpyxl 3.1.5,
then independently evaluated their actual workbook formulas with formulas 1.3.4
in an isolated scratch environment:

| Workbook | Live formula | Calculated | Printed | Status after editing a transaction by +1 |
| --- | --- | ---: | ---: | --- |
| Synthetic deposit, Checks!B7 | `=IF(ISNUMBER(C4),B4+B5-B6,"")` | 2694.97 | 2694.97 | `not_balanced` |
| Synthetic card, Checks!B9 | `=IF(ISNUMBER(C4),B4-B5+B6+B7+B8,"")` | 2716.55 | 2716.55 | `not_balanced` |

The formulas reference transaction cells through SUM/SUMIF helpers. They also
check supplied printed subtotals and running balances; absent required totals
stay blank and yield `cannot_check`. Excel recalculation is forced on load.
Excel cells use native numeric precision and differences rounded to cents;
backend reconciliation remains exact Decimal with no tolerance. Microsoft Excel
itself was unavailable, so evaluation used the independent formula engine.

## Anything not done

No requested implementation or local verification remains undone. The PR is
intentionally left unmerged; merging, deployment and production configuration
changes are outside this task's authorization. All validation used synthetic
data. Arithmetic reconciliation cannot certify every date/description or detect
all equal and opposite mistakes; independent exact-row corpus gates cover the
specified synthetic families, rather than claiming accuracy on real statements.
